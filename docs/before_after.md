# Before / after: ten engineering improvements

Common problems in legacy credit-risk pipelines and how this project handles them.
Each row will link to the script and the evidence once it is implemented.

| # | Common problem | Approach in this project | Stage | Status |
|---|---|---|---|---|
| 1 | Exclusion lists (fraud, VIP, …) hard-coded inside procedures; changing them requires recompiling | `ref_exclusion_list` table with a reason code and validity dates per entry — the engine reads the table, the list is edited as data. **Evidence:** 6,039 clients listed from facts in the data (a credit written off at another lender), none typed in code; a check proves no approved client is on the list — [`05_ref_exclusion_list.sql`](../sql/04_reference/05_ref_exclusion_list.sql), [`03_decision_checks.sql`](../sql/05_decision/03_decision_checks.sql) | 4 | ✅ Done |
| 2 | The same calibration formula copied in many places | Numbers (a, b) per model version in the table `ref_calibration`; the formula once, in the Oracle function `f_calibrate_pd`; PDs read from the view `v_scores`. **Evidence:** for all 712,510 scores (2 models × 356,255 clients) Oracle's PD equals Python's to within 1e-9 — [`05_model_scores.sql`](../sql/99_checks/05_model_scores.sql), [calibration.md](calibration.md) | 3 | ✅ Done |
| 3 | Limit matrix written as a long `CASE`, with gaps at band boundaries | `ref_limit_grid` table (5 PD bands × 3 income bands) + check queries that find gaps and overlaps automatically. **Evidence:** 3 grid checks pass (no gap or overlap in PD or income, lower risk never gets a lower multiple); a separate check proves every client's multiple is the one of its own cell — [`04_ref_limit_grid.sql`](../sql/04_reference/04_ref_limit_grid.sql), [decision_engine.md](decision_engine.md) | 4 | ✅ Done |
| 4 | Thresholds (minimum amount, age, cut-off, income multiple) scattered through code | `ref_rules` table with validity dates, read through one function `f_rule` — the decision engine contains no number of its own. **Evidence:** 9 rules in one table; the PD cut-off was derived by analysis and written there, not typed ([cutoff.md](cutoff.md)); every run stores the rules it used and a rule-set fingerprint in `decision_runs` — [`02_ref_rules.sql`](../sql/04_reference/02_ref_rules.sql), [`02_p_run_decisions.sql`](../sql/05_decision/02_p_run_decisions.sql) | 4 | ✅ Done |
| 5 | Snapshot tables truncated every day — no history | Decisions kept per run date in a partitioned table; a re-run replaces only its own date, every run is logged in `decision_runs`. **Evidence:** the same date was run twice — its part still holds exactly 356,255 decisions, all from the latest run, and both runs remain in the run log — [`01_decision_tables.sql`](../sql/05_decision/01_decision_tables.sql), [`03_decision_checks.sql`](../sql/05_decision/03_decision_checks.sql) | 4 | ✅ Done |
| 6 | Row duplication passes silently | Automatic data-quality checks after each step, logged to `dq_log`; failure stops the run. **Evidence:** grain profiling found 653,483 extra rows in `installments_payments` (one instalment paid in several rows); they are merged per instalment, and a check proves the client table sums back to exactly 12,951,918 instalments. Stage 2 run: 35 of 35 checks passed — [data_profiling.md §4](data_profiling.md#4-grain-what-one-row-means), [`03_dq.sql`](../sql/01_ddl/03_dq.sql) | 2 | ✅ Done |
| 7 | Commented-out blocks and tables filled by unknown processes | Each step is one numbered script, run in a fixed order by one pipeline that stops at the first failure and logs every step. **Evidence:** `run_pipeline.py` lists the script behind every step; the first daily run passed 4 of 4 steps and 16 data-quality checks in 1.4 minutes and reproduced the earlier run exactly (233,377 approvals) — [stage5_design.md](stage5_design.md), [`run_pipeline.py`](../python/scripts/run_pipeline.py) | 5 | ✅ Done |
| 8 | Misleading column names | Naming convention + `COMMENT ON` → generated data dictionary. **Evidence:** 87 feature columns, 0 without a description — [data_dictionary.md](data_dictionary.md), generated by [`04_data_dictionary.sql`](../sql/99_checks/04_data_dictionary.sql) | 2 | ✅ Done |
| 9 | Reject reasons reconstructed after the decision in reporting code | Every reason written at decision time (`decision_reasons`, plus main reason and full list on `decisions`); reports only read them. **Evidence:** every decline has a main reason, it is always the highest-priority one, and the reason rows match the counts on the decisions (checks); the dashboard view `v_decision_summary` only adds them up. Every risk decline also carries the three facts that raised the risk most, in plain words (`decision_risk_factors`) — [decision_engine.md](decision_engine.md), [risk_factors.md](risk_factors.md) | 4 | ✅ Done |
| 10 | Logic split across two engines, unclear which is authoritative | Decision logic and the calibration formula live in Oracle; Python orchestrates, explains and reports, and reconciliations prove both agree. **Evidence:** Python recomputes every decision and limit with the rules in force — 0 differences; Oracle's PD equals Python's for all 712,510 scores within 1e-9; the dashboard files must add up to the engine's run or nothing is written — [decision_engine.md](decision_engine.md), [`05_model_scores.sql`](../sql/99_checks/05_model_scores.sql), [`export_tableau.py`](../python/scripts/export_tableau.py) | 5 | ✅ Done |
