# Decision log

One line per decision: what was decided and why. Newest at the bottom.

| # | Date | Decision | Reason |
|---|---|---|---|
| 1 | 2026-09-25 | Use the Kaggle *Home Credit Default Risk* dataset | Public, realistic credit data with application, bureau, payment and card history — close to a real pre-approval setting |
| 2 | 2026-09-25 | Database: Oracle 18c XE, pluggable database `XEPDB1` | Data belongs in the PDB, not the container root |
| 3 | 2026-09-25 | Dedicated schema `HC` instead of working as `SYSTEM` | Keeps project objects separate from system objects; the whole project can be removed with one command |
| 4 | 2026-09-25 | GitHub is the single source of truth | Tableau Public, Kaggle and LinkedIn receive copies from the repo and link back to it |
| 5 | 2026-09-25 | Raw data is not committed | GitHub file size limit and Kaggle licence; `data/README.md` explains how to download it |
| 6 | 2026-09-25 | Repository language: English | Readable by international reviewers and the Kaggle/GitHub community |
| 7 | 2026-09-25 | Load CSVs through Oracle external tables (`ext_*` → `raw_*`) | Pure SQL, no extra tools; the CSV can be queried before loading; type conversion is explicit and fails loudly |
| 8 | 2026-09-25 | External tables use an explicit record delimiter per file (`0x'0A'` or `0x'0D0A'`) | Oracle 18c has no `DETECTED NEWLINE`; line endings were measured: the Kaggle data files use LF, the column description file uses CRLF |
| 9 | 2026-09-25 | `365243` in `DAYS_*` columns → `NULL` + explicit flag (e.g. `is_not_employed`), in the feature layer only | Measured: in `DAYS_EMPLOYED` it marks all pensioners and unemployed clients, whose default rate is 5.40% vs 8.66% — the information is kept as a flag, while `NULL` keeps averages and linear models correct. The raw layer stays unchanged. See [data_profiling.md](data_profiling.md) |
| 10 | 2026-09-25 | `installments_payments` is aggregated in two steps: payment rows → one row per instalment → one row per client | Measured: 13,605,401 rows describe 12,951,918 instalments — 629,210 instalments were paid in 2 rows, some in up to 12. Counting rows directly would inflate instalment counts by 653,483 and mark a split payment as "underpaid". A DQ check proves the client table sums back to 12,951,918 instalments |
| 11 | 2026-09-25 | `previous_application` keeps only rows with `FLAG_LAST_APPL_PER_CONTRACT = 'Y'` and `NFLAG_LAST_APPL_IN_DAY = 1` | Kaggle documents that one contract can have several applications and that some applications are repeated within a day. Measured: 8,475 and 5,900 such rows. Without the filter, application and refusal counts are inflated |
| 12 | 2026-09-25 | Bureau burden is measured as active debt / income (`bur_debt_to_income`); the bureau annuity sum is kept but documented as understated | Measured: `AMT_ANNUITY` is reported for only 22.2% of active bureau credits (431,549 NULL, 59,259 zero of 630,607), so a monthly obligation built from it would look lower than it is. Debt (`AMT_CREDIT_SUM_DEBT`) is reported far more consistently |
| 13 | 2026-09-25 | Gender (`CODE_GENDER`) is not used as a feature | Fair lending: many jurisdictions prohibit using sex in credit decisions, and a model that sees it can give two otherwise identical applicants different outcomes. The column stays in the raw layer only |
| 14 | 2026-09-25 | Scripts connect through an Oracle Wallet (`CONNECT /@hc_xepdb1`), from one shared file `sql/_connect.sql` | No password is typed or stored in any script; the encrypted wallet lives outside the repository. Connection logic is in one place instead of being repeated in every runner. See [setup_wallet.md](setup_wallet.md) |
| 15 | 2026-09-25 | Python reads features from Oracle and writes scores back with `python-oracledb` in thin mode; the password comes from Windows Credential Manager via `keyring` | Oracle stays the single source of truth, with no CSV copies to keep in sync. Thick mode (which could read the Oracle Wallet) needs Oracle Client 19+, but Oracle 18c XE ships 18.4; thin mode cannot read the wallet. Credential Manager keeps the password encrypted and out of every file. See [setup_wallet.md](setup_wallet.md) |
| 16 | 2026-09-25 | Two models — a WoE scorecard and LightGBM — compared on a holdout; the scorecard wins unless LightGBM is clearly better (Gini gain ≥ 0.02) | The scorecard is fully explainable and can run in SQL; extra accuracy must be worth the loss of simplicity. See [stage3_design.md](stage3_design.md) |
| 17 | 2026-09-25 | The known-outcome clients are split 70 / 15 / 15 (fit / valid / holdout) in Oracle with `ORA_HASH(SK_ID_CURR)`. Age is *offered* to the models like any other feature; it gives no points of its own unless the data calls for it (see decision 20) | A hash split is reproducible on any machine without a random seed and is shared by SQL, Python, Dataiku and Tableau |
| 18 | 2026-09-25 | Documentation is written for non-specialists too: every document starts with "In plain words", terms are explained in [glossary.md](glossary.md) | The project is meant to be understood by anyone who opens it, not only by risk specialists |
| 19 | 2026-09-25 | Scorecard rules: up to 10 starting groups per feature, merged until the default rate moves in one direction; every group at least 5% of clients (small categories join the one with the closest default rate); IV ≥ 0.02; of two features correlated above 0.7 the stronger stays; at most 20 features; a feature with a wrong-sign weight or a points range below 3 is removed and the model refit; 600 points = odds 50:1, +20 points = odds doubled | Every rule keeps the scorecard readable and stable: no zig-zag points, no extreme points from tiny groups, no feature that changes nothing. See [scorecard.md](scorecard.md) |
| 20 | 2026-09-25 | Age is not in the scorecard; any age limit belongs to the decision engine as an explicit, documented eligibility rule — never hidden inside the risk score | The model excluded age by itself (wrong-sign weight: its information is already carried by the external score, employment length and income type). In this data older clients repay *better* (3.6% default at 65+), so a lender's age limit is a policy choice about the loan term — e.g. age at the end of the loan — not a repayment-risk estimate. Kept separate, it is visible, configurable (Stage 4 rules table) and reported as its own reason, instead of silently lowering a score |
| 21 | 2026-09-25 | LightGBM: age is not a feature; its settings are chosen by 5-fold cross-validation inside `fit` from 6 settings declared in advance (tree size × smallest group); `valid` is used only to measure the final model | Age in LightGBM had a zig-zag effect (under 30 "safer" than 30–39) that cannot be explained to a client and contributed only 2.2% — and decision 20 keeps age out of every risk score. Choosing settings inside `fit` keeps `valid` clean, so its Gini compares fairly with the scorecard's, and a small declared grid avoids a lucky pick |
| 22 | 2026-09-25 | New feature `app_credit_term` = credit amount / annuity (the loan's effective term), added before the holdout is opened; all models retrained | Loan structure already ranked high in LightGBM (annuity, instalments left, credit-to-goods) but the term itself was missing. Its mirror image, annuity / credit, was not added: binning and decision trees depend only on the order of values, so it would carry no new information. Any feature change must happen before Stage 3f, because the holdout can be used only once |
| 23 | 2026-09-25 | LightGBM is the model of record; the scorecard is kept as a readable benchmark | Holdout (46,309 clients, used once): Gini 0.572 vs 0.504, gain +0.069 with a 95% bootstrap interval of +0.060 to +0.076 — well above the +0.02 set in advance (decision 16). The 10% it rates riskiest default 47× as often as the 10% it rates safest (29.5% vs 0.6%). Consequences: scores are computed in Python and written to Oracle; each decision's reasons come from SHAP. See [model_comparison.md](model_comparison.md) |
| 24 | 2026-09-25 | Calibration by Platt scaling (PD = 1 / (1 + exp(-(a + b × raw score)))), a and b learned on `valid`; a and b stored in `ref_calibration`, the formula only in `f_calibrate_pd`, raw scores in `model_scores`, calibrated PD read from `v_scores`; Python's PD stored alongside and reconciled | `fit` is excluded because the model is over-confident on clients it learned from; `holdout` is only reported on. Keeping numbers in a table and the formula in one function removes the copied-formula problem (improvement 2); storing raw scores means a new calibration needs no rescoring |
| 25 | 2026-09-25 | Decision engine: rules, reason codes, limit grid and exclusion list are tables read by the engine; the PD cut-off is set so that the default rate among approved clients stays at or below 5%; an age rule applies to age at the end of a 24-month offer (70); every risk decline also gets the 3 facts that raised the client's risk most (SHAP). All numbers are illustrative choices for a public dataset | Rules as data fix improvements 1, 3, 4 and 9. A target default rate is the simplest cut-off rule to explain; the other rules are shown as a trade-off table. The age rule is a visible policy rule, not part of the score (decision 20). Reasons per client are what a declined applicant is usually entitled to. No value is taken from any lender's internal policy. See [stage4_design.md](stage4_design.md) |
| 26 | 2026-09-25 | Decision engine output: `decisions` and `decision_reasons` partitioned by run date (automatic list partitioning), a re-run replaces only its own date; `decision_runs` logs every run with the rules in force and a rule-set fingerprint; the main reason is the one with the lowest priority number; a client whose limit ends below `MIN_LIMIT` gets `DEBT_TOO_HIGH` if the debt cap is the problem and the new `LIMIT_BELOW_MIN` if the grid limit itself is too small; negative bureau balances count as 0 debt | History by date fixes improvement 5 without a daily truncate. With the rule text and fingerprint stored per run, any decision can be explained later with the rules of its day. Two affordability reasons keep the stated reason true: "debt too high" for a client with no debt would be wrong. A negative balance (an overpayment) must not create extra room for new credit. See [stage4_design.md](stage4_design.md) |
| 27 | 2026-09-26 | The debt rule stays at 5 × income (`MAX_TOTAL_DEBT_TO_INCOME`) | Measured on `valid` ([decision_engine.md](decision_engine.md)): without it, approvals would rise from 65% to 80% while trouble among the approved would rise only from 4.7% to 4.9%, and clients declined only by this rule were about as risky as the approved (5.1% vs 4.7% on the holdout). The rule is kept because it protects clients from over-indebtedness (responsible lending), not because it predicts default; its cost in approvals is documented. Changing it would be a new, dated row in `ref_rules` |
| 28 | 2026-09-26 | Every client declined for risk gets the three facts that raised the estimated risk most (LightGBM SHAP values, compared with an average client), as sentences from a text table `ref_feature_text` (one per model feature); only risk-raising facts are named; explanations are refused unless the SHAP parts add up exactly to the stored raw score | A reason code alone does not tell a client what to change. Texts as data keep wording out of code. The reconciliation proves the explanation comes from the very model that made the decision. Facts about personal circumstances (education, family status) are reported, with how often they appear, for a compliance review rather than removed silently. See [risk_factors.md](risk_factors.md) |
